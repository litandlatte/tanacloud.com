# Data — EV charging detection demo

Three CSVs driving the H3 hands-on lab, plus 200-row samples for showing on screen.

> ## ⚠️ All of this data is synthetic
>
> **ABC Corp does not exist.** Neither do the vehicles, the stations, the competitor brands, the
> headings or any charging session in these files. Nothing here is derived from anyone's real
> telematics, commercial or customer data.
>
> What *is* real: the **city coordinates** the data is seeded around, and the broad pattern that
> EV adoption differs sharply between European countries. Those make the maps recognisable. Every
> other value is generated by `make_data.py` from a fixed seed.

## `ev_pings.csv`

Telematics from 3,000 vehicles over one week (Mon 8 – Sun 14 June 2026), reported about every
12 minutes.

**These are real trajectories, not scattered points.** Pings are ordered per vehicle and alternate
between driving and stopping, so a run of consecutive low-speed pings in one place *is* a stop.
That run is the grain the lab works at.

| Column | Type | Unit / format | Notes |
|---|---|---|---|
| `ping_id` | integer | — | Surrogate key |
| `vehicle_id` | string | `EV000000` | 3,000 distinct vehicles |
| `ts_utc` | timestamp | ISO 8601, UTC | 2026-06-08 → 2026-06-14 |
| `lat` | float | degrees, WGS84 | 5 dp (~1 m) |
| `lon` | float | degrees, WGS84 | 5 dp |
| `speed_kmh` | float | km/h | **≤ 5.0 counts as parked** |
| `heading_deg` | float **or empty** | degrees, 0–360 | **Empty for ~14% of pings** |
| `soc_pct` | float | percent | State of charge; rises while charging, falls while driving |

**On `heading_deg` being empty.** That gap is deliberate and realistic: GPS heading is derived from
movement, so trackers routinely drop it or hold a stale value **when the vehicle is stationary** —
precisely when you want it. Any model using heading has to cope with it missing. The lab feeds the
raw value to a gradient-boosting classifier, which handles NaN natively.

Note also that heading must be averaged as a **direction**, not a number: the mean of 350° and 10°
is 0°, not 180°. The lab averages the sine and cosine.

## `ev_stations.csv`

| Column | Type | Notes |
|---|---|---|
| `station_id` | string | `ABC0000` / `CMP0000` |
| `operator` | string | `ABC Corp`, or one of five **fictional** competitor brands |
| `is_abc` | boolean | **The ownership indicator** |
| `lat`, `lon` | float | degrees, WGS84, 5 dp |
| `country` | string | ISO 3166-1 alpha-2, 20 countries |
| `city` | string | Nearest seed city |
| `n_chargers` | integer | 2, 4, 6, 8 or 12 |
| `max_power_kw` | integer | 50 (AC), 150 (DC fast), 350 (ultra-fast) |
| `bay_bearing_deg` | integer | Which way a car faces when plugged in |

**40% of competitor stations are deliberately co-located within 100–400 m of an ABC station.**
Chargers really do cluster — retail parks and motorway services host several operators side by
side — and these neighbours are the hardest negatives in the dataset. A car charging at the
competitor next door has a rising SoC, a long dwell and a bay-aligned heading, metres from an ABC
charger it never touched.

`bay_bearing_deg` is the least realistic column here. Most real station records carry no bay
orientation at all; it exists so the lab can test whether alignment carries signal. Treat it as a
demo affordance, not something you should expect in a production feed.

## `ev_charging_sessions.csv` — the labels

ABC Corp's internal billing records.

| Column | Type | Notes |
|---|---|---|
| `session_id` | string | Unique |
| `station_id` | string | **Always an `ABC` station** |
| `vehicle_id` | string | Vehicle that charged |
| `start_utc`, `end_utc` | timestamp | ISO 8601, UTC |
| `duration_min` | integer | Minutes |
| `energy_kwh` | float | Energy delivered |
| `power_kw` | integer | Station peak power |

### The shape of the problem is the shape of this file

| | Stations | Sessions recorded |
|---|---:|---|
| ABC Corp | 80 | 991 |
| Competitors | 250 | **none, ever** |

That asymmetry is the entire business case. ABC can measure its own network exactly and has **no
visibility at all** into the 250 competitor sites — yet competitor demand is what tells it where
to build. The lab trains on the 80, then scores all 330.

**Competitor charging still happens in the ping data.** Those vehicles show the same rising SoC and
long dwell; they simply leave no record in ABC's systems. When training against ABC stations they
are correctly negative (the car did not charge at *that* station), and at inference the model
should light them up at the competitor site — which is exactly the generalisation being asked for.

## Matching sessions to stops — one to one

A session must claim **exactly one** stop: the one it overlaps most in time. Letting a session
match several nearby stops of the same vehicle silently manufactures false positives, and the
damage is invisible until you measure the distance from each "charging" stop to its own station.

Built correctly, that distance is **median 17 m, 99th percentile 223 m, max 461 m**. An early
version of this dataset had a 90th percentile of **10.8 km** because of exactly this bug.

## Difficulty

Tuned so no single feature is sufficient. Measured on a held-out-by-vehicle split, PR-AUC from
each feature alone:

| Feature | PR-AUC alone |
|---|---:|
| `dist_m` | 0.618 |
| `soc_delta` | 0.457 |
| `align` | 0.344 |
| `n_pings` / `dwell_min` | 0.274 |
| `max_power_kw` | 0.218 |
| `hour` | 0.198 |
| **all combined** | **0.991** |

Distance is the strongest single signal and nowhere near enough on its own. That gap is the point:
it is what makes this a modelling problem rather than a threshold.

## Reproducing

```bash
pip install numpy pandas
python make_data.py .          # rewrites all seven files
```

Seeded (`SEED = 7`) and deterministic: same seed, same bytes. Change it and every figure in the
lab moves.
